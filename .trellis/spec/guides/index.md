# 思考指南

> **目的**：扩展思维，捕捉可能没想到的点。

---

## 为什么需要思考指南

**大多数 bug 和技术债来自"没想到"**，而非能力不足：

- 没想到层边界会发生什么 → 跨层 bug
- 没想到代码模式会重复 → 到处重复的代码
- 没想到边界情况 → 运行时错误
- 没想到未来的维护者 → 不可读的代码

这些指南帮你**在写码前问对问题**。

## 快速参考：思考触发器

### 何时思考跨层问题

- [ ] 新增/修改 **Provider**（触及 providers/ + types.ts + info.json + README）
- [ ] 修改 `SynthesisRequest` 的字段或 `buildSsml` 的输出（多个消费方）
- [ ] 修改参数格式转换（`rateToSpeed` / `pitchToHz` / `volumeToVoicecraftVolume`）
- [ ] 修改 `outputFormat` 默认值（存在入口层与 edge-tts 协议层两处）
- [ ] 不确定逻辑该放哪层（entry / providers / core / util）
- [ ] 修改错误类型或重试语义（`makeError` 的 `type` / `statusCode`）

→ 读 [跨层思考指南](./cross-layer-thinking-guide.md)

### 何时思考代码复用

- [ ] 正在写与已有代码相似的代码
- [ ] 同一模式重复出现 3 次以上
- [ ] 给多处添加同一新字段
- [ ] **正在修改任何常量或配置**（Provider ID、默认语音、UA、语言映射）
- [ ] **正在创建新的工具/辅助函数** ← 先搜索！
- [ ] 多个文件手写了 Base64 / SHA-256 / 重试 / SSML 构建
- [ ] 二进制数据处理未走 `normalizeBytes`

→ 读 [代码复用思考指南](./code-reuse-thinking-guide.md)

### 验证 AI 交叉评审结果时

- [ ] 评审声称"用户输入可能被注入" → 检查实际数据源（`info.json` 固定枚举？还是外部 API 返回？）
- [ ] 评审标记"缺少校验" → 数据是否来自可信内部源（如 `defaultVoices`）？
- [ ] 评审说"行为变化" → 读代码注释——是否是有意设计？
- [ ] 评审在测试中识别"bug" → 心里删掉被测功能，测试是否仍通过？若通过 → 同义反复测试

**常见 AI 评审误报模式**：
1. **信任边界混淆**：把内部数据（`info.json` 固定枚举、`defaultVoices`）当作不可信外部输入
2. **忽略设计注释**：把代码注释中记载的有意行为当 bug 标记（如 edge-tts 的 `'Z'` 时间戳后缀、`MIN_ELAPSED_SEC` 超时防护、`addtion` 拼写）
3. **变量误读**：未追踪变量真实定义（如 `synthesis-request.ts` 里 `locale` 来自 `resolveLocale` 而非 `query.lang`）

**验证规则**：每条 CRITICAL/WARNING 结论必须对照实际代码验证后再排序。AI 评审预算约 35% 误报率。

## 修改前规则（关键）

> **改动任何值之前，务必先搜索！**

```bash
# 搜索即将改动的值
grep -r "value_to_change" .
```

这一习惯能避免大部分"忘了更新 X"类 bug。
